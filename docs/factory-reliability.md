# Factory reliability fixes

The repaired runtime batches a complete authenticated handoff into one model admission. Partial and duplicate fragments do not consume model turns. `factory_handoff_ack` derives the exact canonical receipt from matching journal and watchdog records, while manual protocol sends are validated before transmission. Unknown send outcomes retain durable claims and cannot be retried automatically. Codex, Claude Code and OpenCode expose the same guarded tools.

Fresh supervisors launch from a content-addressed read-only source snapshot under the run directory. The snapshot retains the exact configuration, task packets, source lock and selected mandates. Both launch preparation and runtime admission compare the complete source inventory, detecting new files as well as changes and removals. Installed interpreters and adapter environments remain external dependencies; their entrypoint hashes are recorded and checked, and the snapshot does not claim to copy an entire virtual environment.

Readiness reports and individual observations must carry `factory_source_sha256` for the exact source and selected mandates actually tested. Changing code or mandate content invalidates earlier PASS observations. Historical observations are preserved and cannot be made current by rewriting only the report's hash. A fresh authorized live rehearsal remains necessary before another judged run; local tests do not establish service delivery or model performance.

Use `scripts/runtime --config /absolute/path/to/factory.yaml factory-status` to read current saved runtime, accounting, source, checkpoint and product evidence. It reports observation times and distinguishes persisted status from process liveness. Existing Run 7 records remain stopped/blocked and unchanged by these runtime fixes.

## Bounded runnable checkpoints

Fresh sessions require an ordered `progress.milestones` policy. Each milestone has a unique `id`, positive `max_turns` and `max_seconds`, an exact `command` argv beginning with an absolute executable, `timeout_seconds`, and `max_attempts` (at most ten). The first milestone should be a small runnable smoke checkpoint. Later milestones may check broader behavior. Supply a real check appropriate to the generated task before freezing; a no-op command cannot establish runnable behavior.

The policy is deliberately absent from historical configurations. Do not add it to a live or historical ledger to reset its clocks. `progress_policy(config)` validates the optional schema. A guard is bound to the room, resolved product checkout and policy digest. Changed bindings fail closed.

`ProgressGuard.admit_turn(turn_id)` admits at most the configured number of unique model turns before the next checkpoint. Its time clock starts on the first admitted turn, rather than while a supervisor waits for initial dispatch. Subsequent idle time counts. A duplicate admission identity does not increment the counter. During the final admitted turn, `health(execution_busy=True)` permits the team to finish its checkpoint; subsequent admission is refused without proof. Wall-clock limits apply while a turn is busy too.

The team calls `factory_progress` for checkpoint details and remaining turns, seconds and attempts, then `factory_verify_checkpoint` with `candidate_commit` from an active admitted turn. The implementation invokes `verify_next(candidate_commit, remaining_seconds=...)`. The caller supplies the minimum remaining turn, room and overall execution time. Verification executes only the command frozen in the policy. It first requires a clean checkout at the exact full candidate SHA, executes the check under the smaller command/progress/authorized time limit, then checks the candidate again. Results and bounded redacted output are persisted as a hashed receipt outside the product checkout. A changed checkout, timeout, failure or cancellation cannot advance the milestone. The next milestone starts only after a passing machine observation. **A checkpoint is not independent product acceptance**, and does not bypass QA or review gates.

The tool calls `begin_verification()` synchronously before scheduling its worker. This resets cancellation before scheduling only; `verify_next` never clears a cancellation request. The guard persists its execution claim before running anything, and releases the state lock during Git and command execution so supervisor health checks remain responsive. `cancel_verification()` cancels the owned command process group, including when cancellation arrives before the worker starts. The caller waits for that worker to finish cleanup before returning. An interrupted process with an unresolved claim is an unknown outcome after restart; it is not automatically retried. Attempt counts are bounded. Commands are argv, never shell strings. Command output is capped at 64 KiB per stream and redacted. The owned process group is killed at the timeout/cancellation boundary, with up to two seconds to reap the terminated process.

`status_report(config, mode)` reads the configured accounting ledger, owner snapshot, progress state, product Git HEAD and planning queue, freeze inventory, recorded source snapshot and rehearsal observation metadata. It does not create a supervisor, write evidence, run product tests, connect to BAND or read reasoning logs. It labels owner state as persisted state rather than verified process liveness. Queue acceptance stays a reported claim. A source snapshot is checked on disk without claiming to inspect loaded process memory. Historical rehearsal entries retain their original dates and never become fresh rehearsal proof through a status read.

Local tests use temporary repositories and synthetic operational inputs. They establish control behavior, not live BAND delivery, model performance or product correctness. A fresh rehearsal of the frozen policy and source snapshot remains necessary before another judged run.
